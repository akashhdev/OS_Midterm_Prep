1. Short Answer: Your answers should be as concise as possible; aim for three or four sentences.
2011Q1.1 (5 pt) Explain why implementing synchronization primitives by disabling interrupts is not appropriate in a single-processor system if the synchronization primitives are to be used in user-level programs.
ANSWER

Disabling interrupts works on a uniprocessor only for trusted kernel code. It is the wrong tool for user-level synchronization because:

  1. It is a privileged instruction. Letting user programs execute it breaks dual-mode protection; the hardware traps if user mode tries.
  2. The OS loses control of the CPU. While interrupts are off, the timer interrupt cannot fire, so no preemption or context switch can happen. A buggy or malicious program could disable interrupts and never re-enable them (e.g. an infinite loop in its critical section). It would then monopolize the CPU and hang the whole system.
  3. Other events are delayed or lost. I/O-completion interrupts and clock ticks are postponed, so devices sit idle, the system clock drifts and response time suffers. User critical sections can be long, which makes this worse.

(It also does not scale: on a multiprocessor it only stops the local CPU.) User programs should instead use OS-provided semaphores/mutexes or atomic hardware instructions such as test_and_set or swap.

2011Q1.2 (5 pt) Provide an example in which multithreading does not provide better performance than a single-threaded solution.
ANSWER

Multithreading helps only if there is work that can overlap. Two examples where it does not help:

  • A strictly sequential computation, where each step depends on the previous result. Examples are computing a tax return or a recurrence such as Fibonacci with an iterative loop. There is nothing to run in parallel, and threads only add creation, context-switch and synchronization overhead.
  • A CPU-bound program on a single processor with no I/O (e.g. a matrix multiply). The threads just take turns on the same CPU, so the total time is the same or worse because of switching overhead.

Another standard example is a shell or interactive program that only waits for one user's input. It spends its time blocked anyway.

2011Q1.3 (5 pt) Show that, if the wait() and signal() semaphore operations are not executed atomically, then mutual exclusion may be violated.
ANSWER

Busy-waiting definitions: wait(S){ while (S <= 0); S--; } and signal(S){ S++; }, with S = 1 (unlocked).

If wait() is not atomic, the test and the decrement can be interleaved:

StepP0P1S
1tests S<=0 → false (S=1)1
2preemptedtests S<=0 → false (S=1)1
3S-- ; enters critical section0
4S-- ; enters critical section−1

Both P0 and P1 are in the critical section, so mutual exclusion is violated. Likewise, S-- and S++ are each load, modify, store at machine level. If two processes run them concurrently, an update can be lost, e.g. two signal() calls increment S only once. A lost signal can block a process forever, and an extra count lets two processes in. So wait() and signal() must be indivisible.

2. Consider a multiprocessor system and a multithreaded program written using the many-to-many threading model. Let the number of user-level threads in the program be more than the number of processors in the system. Discuss the performance implications of the following scenarios.
2011Q2.1 (5 pt) The number of kernel threads allocated to the program is less than the number of processors.
ANSWER

Fewer kernel threads than processors. The kernel can schedule only that many of the program's threads at once. Some processors are left idle as far as this program is concerned, and the available parallelism is wasted. Also, if a kernel thread blocks (e.g. on I/O), even fewer user threads can run.

2011Q2.2 (5 pt) The number of kernel threads allocated to the program is equal to the number of processors.
ANSWER

Equal to the number of processors. All processors can run the program's threads simultaneously, giving the best case while no thread blocks. However, when a kernel thread blocks (I/O, page fault, system call), its processor becomes idle. No spare kernel thread exists to run another ready user thread on it, so performance drops during blocking.

2011Q2.3 (5 pt) The number of kernel threads allocated to the program is greater than the number of processors but less than the number of userlevel threads.
ANSWER

More kernel threads than processors, but fewer than user threads. This gives the best utilization. When one kernel thread blocks, the kernel can schedule another ready kernel thread (carrying another user thread) on that processor, so CPUs stay busy. The cost is some extra kernel overhead: more kernel threads to create, schedule and context-switch.

3. Multilevel queue scheduling
2011Q3.1 (2 pt) List two possible scheduling among queues, which we discussed in class.
ANSWER

Two ways to schedule among the queues of a multilevel queue:

  1. Fixed-priority (preemptive) scheduling. Serve all processes in a higher-priority queue (e.g. foreground/interactive) before any process in a lower queue (background/batch). A process arriving in a higher queue preempts a lower one. Lower queues may starve.
  2. Time slicing among queues. Each queue gets a fixed share of CPU time, which it schedules among its own processes. Example: 80% to the foreground queue (RR) and 20% to the background queue (FCFS).
2011Q3.2 (8 pt) Describe how Linux support the above two possible inter-queue scheduling.
ANSWER

Fixed priority between classes. Linux has two priority ranges mapped onto one global scale (lower number = higher priority). Real-time tasks are 0–99 and use POSIX SCHED_FIFO / SCHED_RR with static priorities. Normal (time-sharing) tasks are 100–139, from nice −20…+19. A runnable real-time task always runs before any normal task, which is fixed-priority scheduling between the two "queues". With CFS, the scheduler likewise picks the highest-priority scheduling class first (real-time class before the default class).

Time slicing. In the O(1) scheduler (2.5) each task gets a time slice based on priority, and higher priority gets a longer quantum. Each CPU's runqueue has an active and an expired priority array. A task runs while it has slice left, then moves to expired. When the active array is empty, the arrays are swapped, so every task gets its share. In CFS (2.6.23+), instead of fixed quanta each task gets a proportion of CPU time within a target latency, weighted by nice value. The task with the smallest virtual runtime (vruntime) runs next. This is proportional sharing of time.

2011Q6 (15 pt) Discuss how the following pairs of scheduling criteria conflict in certain settings.
2011Qa) CPU utilization and response time
ANSWER

CPU utilization vs. response time. CPU utilization is highest when context switches are rare, as with FCFS or a long quantum, because each switch is pure overhead. Good response time for interactive users needs frequent preemption (a short RR quantum) so every user gets the CPU quickly. That causes many context switches, so the CPU spends more time switching and less doing useful work, which lowers utilization.

2011Qb) Average turnaround time and maximum waiting time
ANSWER

Average turnaround time vs. maximum waiting time. Average turnaround is minimized by running the shortest jobs first (SJF/SRTF). But a long job can be postponed again and again as short jobs keep arriving, so it may starve. Its waiting time, the maximum waiting time, becomes very large (unbounded). Bounding the maximum wait (e.g. with FCFS or aging) raises the average turnaround.

2011Qc) I/O device utilization and CPU utilization
ANSWER

I/O device utilization vs. CPU utilization. Keeping devices busy means running I/O-bound processes as soon as their I/O completes, so they can issue the next request quickly. This means frequently preempting CPU-bound processes, and the context-switch overhead lowers CPU utilization. Maximizing CPU utilization means letting CPU-bound jobs run long without switching, which leaves the I/O devices idle while I/O-bound jobs wait for the CPU.

2011Qd) Deadline and fairness
ANSWER

Deadline vs. fairness. To meet deadlines, the scheduler must always give the CPU to the most urgent process (earliest deadline or real-time priority), regardless of how much CPU it has already had. Other processes may wait a long time or starve, which is unfair. A fair scheduler gives everyone an equal share, so urgent tasks may not get enough CPU in time and miss their deadlines.

2011Qe) Throughput and context switch overhead
ANSWER

Throughput vs. context-switch overhead. Throughput (jobs completed per unit time) is improved by finishing short jobs quickly, which needs preemption: SJF/SRTF or a small RR quantum. Every preemption adds context-switch overhead, during which no useful work is done. Minimizing switches (FCFS, large quantum) traps short jobs behind long ones (convoy effect), so fewer jobs complete per unit time. If the quantum is too small, overhead itself eats the throughput.

2011Q7 (20 pt) Consider the following Peterson's solution for the critical region problem:
shared int turn;              /* set to i or j */
shared boolean flag[2];       /* set to T or F */

while (TRUE) {
    ...
    flag[i] = TRUE;
    turn = j;
    while (turn == j && flag[j] == TRUE) { /* no-op */ }
    ...
    /* critical region */
    ...
    flag[i] = FALSE;
    ...
    /* remainder region */
    ...
}
Prove Peterson's solution satisfy the three required critical region conditions.
ANSWER

Pi enters its critical region only when flag[j] == FALSE or turn == i.

1. Mutual exclusion. Suppose P0 and P1 were both in their critical regions. Then flag[0] = flag[1] = TRUE, so each must have passed the while because turn equalled its own index. That would require turn == 0 and turn == 1 at the same time, which is impossible. More precisely, turn is a single shared variable holding the value written last. The process that wrote turn last set it to the other process's index, so it must wait while the other is interested. Hence at most one is inside.

2. Progress. If Pj is not trying to enter (flag[j] == FALSE, i.e. it is in its remainder region), Pi passes the while at once. If both are trying, turn is either i or j, so exactly one of them passes, and the decision is made in finite time. Only processes in their entry sections take part; a process in its remainder section cannot block anyone.

3. Bounded waiting. Suppose Pi is waiting (turn == j and flag[j] == TRUE). When Pj leaves, it sets flag[j] = FALSE, so Pi can enter. If Pj immediately tries again, it sets turn = i, so Pj now waits and Pi enters. Pi therefore waits for at most one entry of Pj into its critical region.

2011Q8 (Bonus: 20 pt) Consider the code below as a variation of Peterson's solution above:
shared int turn;              /* set to i or j */
shared boolean flag[2];       /* set to T or F */

while (TRUE) {
    ...
    flag[i] = TRUE;
    turn = i;     /* traditionally set to j */
    while (turn == j && flag[j] == TRUE) { /* no-op */ }
    ...
    /* critical region */
    ...
    flag[i] = FALSE;
    turn = j;     /* not usually done */
    ...
    /* remainder region */
    ...
}
Does the above solution satisfy the three required critical region conditions? If not, which property or properties is violated?
ANSWER

No. Mutual exclusion is violated. In the entry code each process now sets turn to its own index, so a process that has just written turn never waits (its test turn == j is false). Counter-example:

StepP0P1
1flag[0] = TRUE; turn = 0
2test turn==1? false → enters CR
3(in critical region)flag[1] = TRUE; turn = 1
4(in critical region)test turn==0? false → enters CR

Both are in the critical region. In general a newly arriving process always gets in, even while the other is inside. (Progress and bounded waiting still hold: a waiting Pi enters as soon as Pj exits, because the exit sets turn = i. But without mutual exclusion the solution is incorrect.)

2013Q1.2 (6 pt) What is busy-waiting in the discussion of critical section problem? Explain how busy-waiting may degrade the system performance, or even deadlock?
ANSWER

Busy waiting (spinning) means a process waiting to enter its critical section repeatedly executes a loop that tests a condition, e.g. while (test_and_set(&lock)); or while (S <= 0);. It never gives up the CPU while waiting.

Performance: the spinning process wastes CPU cycles that other processes could use. On a uniprocessor this is even worse: the spinner burns its whole time slice, and the lock holder cannot run during that time to finish and release the lock. So waiting gets longer and throughput drops.

Deadlock: with priority scheduling, suppose a high-priority process H spins on a lock held by a low-priority process L. H is always runnable, so the scheduler never runs L. L can never release the lock, and H spins forever. Both are stuck (a priority-inversion deadlock).

Fix: a blocking semaphore, where a waiting process sleeps on a queue instead of spinning.

2013Q1.3 (6 pt) In class, we discuss the bounded buffer problem which uses two semaphore, empty and full. Explain the usage of these two semaphores.
ANSWER

Three semaphores protect a buffer of n slots: mutex = 1 (mutual exclusion on the buffer), empty = n and full = 0.

  • empty counts empty slots. The producer calls wait(empty) before inserting, so it blocks when the buffer is full. The consumer calls signal(empty) after removing an item.
  • full counts filled slots. The consumer calls wait(full) before removing, so it blocks when the buffer is empty. The producer calls signal(full) after inserting.
Producer:                        Consumer:
do {                             do {
    /* produce item */               wait(full);
    wait(empty);                     wait(mutex);
    wait(mutex);                     /* remove item */
    /* add item to buffer */         signal(mutex);
    signal(mutex);                   signal(empty);
    signal(full);                    /* consume item */
} while (true);                  } while (true);

Together they replace busy-wait loops, so all n slots can be used. Order matters: calling wait(mutex) before wait(empty) can deadlock.

2013Q1.4 (5 pt) Illustrate how the two process scheduling criteria, CPU utilization and throughput, may conflict with each other?
ANSWER

CPU utilization measures how busy the CPU is; throughput measures how many processes complete per unit time. Maximizing one can hurt the other:

  • Running long CPU-bound jobs keeps the CPU near 100% busy (high utilization). But each job takes a long time, so few jobs finish per unit time (low throughput). Short jobs stuck behind them also delay completion (convoy effect).
  • Favoring many short jobs (SJF, short quantum) completes more jobs per unit time (high throughput). But it causes more context switches, whose overhead is not useful work, and short I/O-bound jobs leave the CPU idle while they wait on I/O. So utilization drops.
2013Q1.5 (6 pt) What happens if one thread of a multi-threaded process call fork()? What happens if one thread of a multi-threaded process call exec()?
ANSWER

fork(): this depends on the system. Some UNIX systems provide two versions of fork(). One duplicates all threads of the process. The other (the POSIX behaviour) duplicates only the thread that called fork(), so the child is single-threaded. If exec() is called right after fork(), duplicating only the calling thread is enough, because exec replaces everything anyway. If the child does not call exec, duplicating all threads may be needed.

exec(): exec works as usual. The program named in its parameter replaces the entire process, including all of its threads. The other threads are destroyed, and the new program starts with a single thread.

2013Q2 (10 pt) A variation of the round-robin scheduler is the regressive round-robin scheduler. This scheduler assigns each process a time quantum and a priority. The initial value of a time quantum is 50 milliseconds. However, every time a process has been allocated the CPU and uses its entire time quantum (does not block for I/O), 10 milliseconds is added to its time quantum, and its priority level is boosted. (The time quantum for a process can be increased to a maximum of 100 milliseconds.) When a process blocks before using its entire time quantum, its time quantum is reduced by 5 milliseconds, but its priority remains the same. What type of process (CPU-bound or I/O-bound) does the regressive round-robin scheduler favor? Explain.
ANSWER

It favors CPU-bound processes.

  • A process that uses its entire quantum (does not block for I/O) is CPU-bound behaviour. It is rewarded: +10 ms of quantum, up to 100 ms, and a priority boost.
  • A process that blocks before using its quantum is I/O-bound / interactive behaviour. It is penalized: −5 ms of quantum, and its priority is not raised.

So over time CPU-bound (batch) processes get longer time slices and higher priority, and I/O-bound processes get shorter slices and stay at lower priority. This is the opposite of the usual goal of favoring interactive processes.

2013Q3 (10 pt) Can a multi-threaded solution using multiple user-level threads achieve better performance on a multiprocessor system, which uses the many-to-one threading model, than on a single processor system? Explain.
ANSWER

No, not significantly. In the many-to-one model, all user-level threads of the process are mapped onto one kernel thread. The kernel schedules only kernel threads, so it sees the process as a single schedulable entity. It can run on only one processor at a time, which means only one user thread executes at any moment even if other CPUs are idle. The program gets no parallelism, and its performance is essentially the same as on a single processor. Also, if any thread makes a blocking system call, the whole process (all threads) blocks.

(The only gain is indirect: other processes can use the other CPUs, so the program may face less competition.) To benefit from multiple processors you need one-to-one or many-to-many threading.

2013Q4.2 (5 pt) Why is it important for the scheduler to distinguish I/O-bound programs from CPU-bound programs?
ANSWER

I/O-bound and CPU-bound processes behave very differently. I/O-bound processes have many short CPU bursts. CPU-bound processes have few, long bursts.

  • If an I/O-bound process gets the CPU quickly, it issues its next I/O request soon and then gets out of the way. The devices stay busy while CPU-bound processes use the CPU, so both CPU and I/O utilization improve.
  • I/O-bound processes are usually interactive, so serving them first gives good response time.
  • If they wait behind long CPU bursts (convoy effect), devices go idle and users see poor response.

So the scheduler should give I/O-bound processes higher priority and short quanta, and give CPU-bound processes lower priority with longer quanta (fewer switches).

2013Q4.3 (6 pt) Modify multilevel queue scheduling so it can distinguish I/O-bound programs from CPU-bound programs.
ANSWER

Change it into a multilevel feedback queue, where a process can move between queues based on its observed CPU bursts:

  • A new process enters Q0 (small quantum). If it uses the full quantum, it is behaving CPU-bound and is demoted to Q1, then to Q2.
  • If it blocks for I/O before its quantum expires, it is I/O-bound and stays in, or is promoted to, a higher queue.
  • Aging: a process that waits too long in a low queue is moved up, which prevents starvation.

So I/O-bound processes end up in high-priority, short-quantum queues and CPU-bound processes in low-priority, long-quantum queues. Parameters: number of queues, algorithm per queue, promotion rule, demotion rule, entry queue.

2013Q5.1 (5 pt) Write to demonstrate how to use the atomic instruction TestAndSet for critical section problem.
ANSWER
boolean test_and_set(boolean *target) {   /* executed ATOMICALLY by hardware */
    boolean rv = *target;
    *target = true;
    return rv;
}

boolean lock = false;                     /* shared */

do {
    while (test_and_set(&lock))
        ;                                 /* spin while lock was already true */
    /* critical section */
    lock = false;                         /* release */
    /* remainder section */
} while (true);

The first process to call test_and_set gets back false (the lock was free) and has atomically set lock to true, so it enters. Every other caller gets true and keeps looping until the holder sets lock = false. This gives mutual exclusion. (Bounded waiting needs an extra waiting[] array.)

2013Q5.3 (5 pt) Write to demonstrate how to use the atomic instruction Swap for critical section problem.
ANSWER
/* swap: executed ATOMICALLY by hardware */
void swap(boolean *a, boolean *b) {
    boolean temp = *a;
    *a = *b;
    *b = temp;
}

boolean lock = false;           /* shared */
boolean key;                    /* local to each process */

do {
    key = true;
    while (key == true)
        swap(&lock, &key);  /* key=old lock; lock=true */
    /* critical section */
    lock = false;
    /* remainder section */
} while (true);

A process loops until a swap returns key = false, meaning the lock was free. That same swap atomically set lock = true, so only one process gets out of the loop. The others keep getting key = true until lock is reset to false.

2013Q5.4 (5 pt) Illustrate how your solution will fail if Swap is not atomic.
ANSWER

If swap is not atomic, the three steps (temp=*a; *a=*b; *b=temp) of two processes can interleave. Start with lock = false, and each process has key = true:

StepP0P1lock
1temp0 = lock → falsefalse
2preemptedtemp1 = lock → falsefalse
3lock = key1 (true); key1 = temp1 = false → enters CStrue
4lock = key0 (true); key0 = temp0 = false → enters CStrue

Both read the old value false before either wrote true, so both leave the loop. Mutual exclusion is violated.

2013Q6 (10 pt) Race conditions are possible in many computer systems. Consider a banking system with two methods: deposit(amount) and withdraw(amount). These two methods are passed the amount that is to be deposited or withdrawn from a bank account. Assume that a husband and wife share a bank account and that concurrently the husband calls the withdraw() method and the wife calls deposit().
(The question stops here on the paper. The textbook version asks: describe how a race condition is possible and what might be done to prevent it.)
ANSWER

deposit() does balance = balance + amount and withdraw() does balance = balance - amount. At machine level each is load balance → modify in a register → store balance, which is not atomic. Suppose balance = 100, the husband withdraws 50 and the wife deposits 50 (the correct result is 100):

StepHusband: withdraw(50)Wife: deposit(50)balance
1reg1 = balance (100)100
2reg2 = balance (100)100
3reg1 = 100 − 50; balance = 5050
4reg2 = 100 + 50; balance = 150150

The withdrawal is lost, and the result would be 50 if steps 3 and 4 were swapped. The outcome depends on the order of execution, which is a race condition.

Prevention: make the update a critical section, so only one method can touch balance at a time. Use a lock or semaphore (wait(mutex); balance ±= amount; signal(mutex);), a monitor, or synchronized methods.

2013Q7 (6 pt) Consider the following code segment:
pid_t pid;

    fork();

ANSWER

2019Q1.1 (5 pt) Ordinarily the exec() system call follows the fork(). Explain what would happen if a programmer were to inadvertently place the call to exec() before the call to fork().
ANSWER

exec() replaces the calling process's entire memory image (code, data, heap, stack) with the program named in its parameters. On success, it never returns.

So if exec() is placed before fork(), the new program starts running in place of the original one, under the same process ID. The rest of the original code, including the fork() call, is gone and never executed. No child process is created, and the original program's remaining work is not done.

Only if exec() fails (returns −1) does execution continue to the fork().

ANSWER

The other (the POSIX behaviour) duplicates only the thread that called fork(), so the child is single-threaded. If exec() is called right after fork(), duplicating only the calling thread is enough, because exec replaces everything anyway. 2019Q1.3 (5 pt) What is processor affinity? Explain why it needed to be considered during process scheduling on multiple CPU systems.
ANSWER

Processor affinity: a process has an affinity for the processor it is currently running on. It is kept on (or restricted to) that same CPU rather than migrated to another one.

7. Multilevel queue scheduling
2019Q7.1 (5 pt) List two possible scheduling among queues, which we discussed in class.
ANSWER

Two ways to schedule among the queues of a multilevel queue:

  1. Fixed-priority (preemptive) scheduling. Serve all processes in a higher-priority queue (e.g. foreground/interactive) before any process in a lower queue (background/batch). A process arriving in a higher queue preempts a lower one. Lower queues may starve.

faculty interactive process
student interactive process
faculty batch process

2020Q5 (15 pt) Discuss how the following pairs of scheduling criteria conflict in certain settings.
2020Q5.1 CPU utilization and response time
ANSWER

CPU utilization vs. response time. CPU utilization is highest when context switches are rare, as with FCFS or a long quantum, because each switch is pure overhead. Good response time for interactive users needs frequent preemption (a short RR quantum) so every user gets the CPU quickly. That causes many context switches, so the CPU spends more time switching and less doing useful work, which lowers utilization.

2020Q5.2 Average turnaround time and maximum waiting time
ANSWER

Average turnaround time vs. maximum waiting time. Average turnaround is minimized by running the shortest jobs first (SJF/SRTF). But a long job can be postponed again and again as short jobs keep arriving, so it may starve. Its waiting time, the maximum waiting time, becomes very large (unbounded). Bounding the maximum wait (e.g. with FCFS or aging) raises the average turnaround.

2020Q5.3 I/O device utilization and CPU utilization
ANSWER

I/O device utilization vs. CPU utilization. Keeping devices busy means running I/O-bound processes as soon as their I/O completes, so they can issue the next request quickly. This means frequently preempting CPU-bound processes, and the context-switch overhead lowers CPU utilization. Maximizing CPU utilization means letting CPU-bound jobs run long without switching, which leaves the I/O devices idle while I/O-bound jobs wait for the CPU.

2020Q5.4 Deadline and fairness
ANSWER

Deadline vs. fairness. To meet deadlines, the scheduler must always give the CPU to the most urgent process (earliest deadline or real-time priority), regardless of how much CPU it has already had. Other processes may wait a long time or starve, which is unfair. A fair scheduler gives everyone an equal share, so urgent tasks may not get enough CPU in time and miss their deadlines.

2020Q5.5 Throughput and context switch overhead
ANSWER

Throughput vs. context-switch overhead. Throughput (jobs completed per unit time) is improved by finishing short jobs quickly, which needs preemption: SJF/SRTF or a small RR quantum. Every preemption adds context-switch overhead, during which no useful work is done. Minimizing switches (FCFS, large quantum) traps short jobs behind long ones (convoy effect), so fewer jobs complete per unit time. If the quantum is too small, overhead itself eats the throughput.

7. Consider the Intel address translation scheme shown in the following.
CPU→logical address→segmentation unit→linear address→paging unit→physical address→physical memory
2020Q7.1 (10 pt) Illustrate all the steps that the Intel 80386 takes in translating a logical address into a physical address.
ANSWER
  1. The CPU generates a logical address = (selector, offset). The 16-bit selector has s = 13-bit segment number, g = 1 bit choosing GDT or LDT, and p = 2 protection bits.
  2. The segmentation unit uses s and g to fetch the 8-byte segment descriptor from the LDT (private segments) or GDT (shared segments). Descriptors are cached in segment registers. It checks the offset against the segment limit and the access rights, trapping on a violation, then computes the linear address = base + offset (32 bits).
  3. The paging unit splits the linear address into p1 (10 bits) | p2 (10 bits) | d (12 bits). Register CR3 points to the current page directory. p1 selects a directory entry, which points to a page table. p2 selects the page-table entry, which gives frame f.
  4. Physical address = f concatenated with d, which is sent to memory. (For 4 MB pages the directory entry points straight at the frame, with a 22-bit offset. The TLB caches recent translations.)
2020Q7.2 (5 pt) What are the advantages to the operating system of hardware that provides such complicated memory translation hardware?
ANSWER
  • Segmentation matches the programmer's view (code, data and stack as separate logical units). It gives per-segment protection (e.g. read-only, execute-only code, privilege levels) and easy sharing of whole segments between processes.
  • Paging on top removes external fragmentation. Segments need not be contiguous in physical memory; they are allocated in fixed-size frames, so allocation is simple.
  • The OS gets flexibility: pages can be swapped or loaded on demand (virtual memory), shared at page level, and protected with page bits. The hardware does the work at memory speed, so the OS does not translate in software.
2020Q7.3 (5 pt) Are there any disadvantages to this address-translation system? If so, what are they? If not, why is it not used by every manufacturer?
ANSWER

Yes.

  • Slower access: without TLB hits, each reference needs a segment-descriptor lookup plus two page-table memory accesses (directory and table) before the data access itself.
  • Complexity and cost: more hardware (segment registers, descriptor tables, MMU, TLB), more chip area and power. The OS must manage both segment tables and page tables.
  • Memory overhead for the tables, and paging still has internal fragmentation.

Because of this cost and complexity, many manufacturers (most RISC designs, ARM, and x86-64 in practice with a flat segment model) use paging only. It delivers most of the benefit with simpler, faster hardware.

But a long job can be postponed again and again as short jobs keep arriving, so it may starve. Its waiting time, the maximum waiting time, becomes very large (unbounded). Bounding the maximum wait (e.g. with FCFS or aging) raises the average turnaround.

2021Q5.3 I/O device utilization and CPU utilization
ANSWER

I/O device utilization vs. CPU utilization. Keeping devices busy means running I/O-bound processes as soon as their I/O completes, so they can issue the next request quickly. This means frequently preempting CPU-bound processes, and the context-switch overhead lowers CPU utilization. Maximizing CPU utilization means letting CPU-bound jobs run long without switching, which leaves the I/O devices idle while I/O-bound jobs wait for the CPU.

2021Q5.4 Deadline and fairness
ANSWER

Deadline vs. fairness. To meet deadlines, the scheduler must always give the CPU to the most urgent process (earliest deadline or real-time priority), regardless of how much CPU it has already had. Other processes may wait a long time or starve, which is unfair. A fair scheduler gives everyone an equal share, so urgent tasks may not get enough CPU in time and miss their deadlines.

2021Q5.5 Throughput and context switch overhead
ANSWER

Throughput vs. context-switch overhead. Throughput (jobs completed per unit time) is improved by finishing short jobs quickly, which needs preemption: SJF/SRTF or a small RR quantum. Every preemption adds context-switch overhead, during which no useful work is done. Minimizing switches (FCFS, large quantum) traps short jobs behind long ones (convoy effect), so fewer jobs complete per unit time. If the quantum is too small, overhead itself eats the throughput.

2021Q7.1 (5 pt) What is busy-waiting in the discussion of critical section problem? Explain how busy-waiting may degrade the system performance.
ANSWER

Busy waiting (spinning) means a process waiting to enter its critical section stays in a loop that keeps testing a condition until it can enter, e.g. while (test_and_set(&lock)); or while (S <= 0);. It never gives up the CPU while waiting.

Degraded performance: the waiting process wastes CPU cycles doing no useful work, and other ready processes could have used them. If the spinner has higher priority than the lock holder, the holder may never run, and the system can even deadlock (priority inversion). Busy waiting is acceptable only for very short waits on multiprocessors, where it avoids a context switch.

2021Q7.2 (10 pt) How to implement semaphore without busy-waiting using block and wakeup? You need to write down the definition of data structure semaphore and wait and signal operations.
ANSWER

Each semaphore has an integer value and a queue of waiting processes. Instead of spinning, a process that must wait is blocked (moved to the waiting state and placed on the semaphore's queue). signal wakes up one waiting process (moves it to the ready queue).

typedef struct {
    int value;
    struct process *list;  /* queue of waiting PCBs */
} semaphore;

void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        add this process to S->list;
        block();               /* running -> waiting */
    }
}

void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        remove a process P from S->list;
        wakeup(P);             /* waiting -> ready */
    }
}

If value is negative, |value| is the number of waiting processes. block() and wakeup() are system calls. wait() and signal() must still be atomic: disable interrupts inside them on a uniprocessor, or use a spinlock on a multiprocessor. That busy wait is limited to these few instructions, so it is short and rare.

2022Q1 (5 pt) Explain why implementing synchronization primitives by disabling interrupts is not appropriate in a single-processor system if the synchronization primitives are to be used in user-level programs.
ANSWER

Disabling interrupts works on a uniprocessor only for trusted kernel code. It is the wrong tool for user-level synchronization because:

  1. It is a privileged instruction. Letting user programs execute it breaks dual-mode protection; the hardware traps if user mode tries.
  2. The OS loses control of the CPU. While interrupts are off, the timer interrupt cannot fire, so no preemption or context switch can happen. A buggy or malicious program could disable interrupts and never re-enable them (e.g. an infinite loop in its critical section). It would then monopolize the CPU and hang the whole system.
  3. Other events are delayed or lost. I/O-completion interrupts and clock ticks are postponed, so devices sit idle, the system clock drifts and response time suffers. User critical sections can be long, which makes this worse.

(It also does not scale: on a multiprocessor it only stops the local CPU.) User programs should instead use OS-provided semaphores/mutexes or atomic hardware instructions such as test_and_set or swap.

2022Q2 (15 pt) Note that only one process is active within the monitor. Suppose A associated with the condition variable q is resumed when B invokes q.signal(). We discussed two possibile solutions in class. One is signal and wait, and the flow is illustrated in the following (Hoare semantics). Please modify the Hoare semantics and depict the other solution (i.e., signal and continue).
ANSWER

Signal-and-continue: when B executes q.signal(), B keeps running in the monitor. The waiting process A is only moved from q's wait queue to a ready/re-entry queue (the "signal queue" now holds the signaled process). A resumes after B leaves the monitor or waits.

Compared with Hoare: in Hoare's version A runs immediately and the signaler B waits in the signal queue. In signal-and-continue, A may find the condition changed by the time it runs, so waiters should re-check it with while (!cond) q.wait();. There are fewer context switches, and this is what Java and Pthreads use.

2022Q4 (10 pt) Suppose a architecture use 48-bit addressing with 4K paging on 64-processors. How much memory space a process may have? How many entries a page table may have? How should a page table be stored in memory?
ANSWER

Memory space per process: 48-bit addresses give 248 bytes = 256 TB of logical address space.

Page-table entries: 4 KB = 212 gives a 12-bit offset, so the page number is 48 − 12 = 36 bits. That makes 236 ≈ 68.7 billion (64 G) entries. On a 64-bit processor each entry is 8 bytes, so a single flat table would need 236 × 8 = 239 B = 512 GB per process.

How to store it: a flat table is far too large to keep, let alone contiguously. Page the page table with a multi-level (hierarchical) page table. x86-64 uses 4 levels:

level 4: 9 bitslevel 3: 9 bitslevel 2: 9 bitslevel 1: 9 bitsoffset: 12 bits

Each table at each level has 29 = 512 entries × 8 B = 4 KB, exactly one page, so tables are paged themselves. Only the tables for parts of the address space actually in use are allocated, which keeps the memory cost small. Alternatives: a hashed page table (good for sparse 64-bit spaces) or an inverted page table (one entry per physical frame). A TLB hides the extra memory accesses.
